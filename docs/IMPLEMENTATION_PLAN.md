# 分阶段实施路线图

目标是尽快实现可靠的最小闭环，而不是一次性搭建复杂框架。完成每个阶段后更新本文件状态与 `docs/PLAN.md`。

## Phase 0：格式与仓库基线

任务：

1. 建立 Python 项目、CLI 入口、配置加载和日志框架。
2. 阅读并记录当前 SillyTavern Character Card V2 / World Info 格式要求；记录对应来源日期。
3. 建立最小合法角色卡和世界书 fixture；编写解析/序列化往返测试。
4. 确定 Tavo 最终导入验证清单；本阶段不能声称已经在 Tavo 实测。
5. 不调用 API，不处理整本书。

验收：

- `python -m ... --help` 可运行。
- 单元测试可在离线状态通过。
- 示例 JSON 可以解析，字段映射有源文档依据。
- `.env` 和 API 凭据被 `.gitignore` 排除。

## Phase 1：导入与章节索引

输入先支持 UTF-8 TXT/Markdown。DOCX/EPUB/PDF 作为后续增量功能，不要在 MVP 同时实现所有格式。

任务：

1. 保留原文件只读，生成 manifest 和 SHA-256。
2. 检测章节标题；支持用户提供章节规则或在识别不确定时生成候选而不是假装准确。
3. 分块时尽量不跨章节，记录 chapter ID、行号/段落范围、字符 offset、块 hash。
4. 保存每个 run 的 manifest 和状态。

验收：

- 对无章节标题文本也能给出明确的 fallback。
- 块能按顺序无丢失/无重复地重组为原文本（除明确的规范化处理外）。
- 中断后可以继续而不重复处理已完成块。

## Phase 2：分块信息提取

任务：

1. 从每个 chunk 提取原子事实：人物、别名、外貌、身份、行为证据、目标、关系、地点、组织、规则、能力/物品、事件。
2. 每个事实要求 source refs 和短证据；不确定项标记 inference/unknown。
3. 保存模型原始响应与经过 schema 校验的结果；非法 JSON 有有限重试并留错误记录。
4. 支持缓存和 checkpoint；prompt 版本或源 chunk 改动应令对应缓存失效。

验收：

- 每项抽取事实都能追溯到 chunk/章节；没有来源的内容不能标为 canon。
- 可使用 mock client 跑完测试而不访问网络。
- 对 API 限流、超时、无效 JSON、输出截断有测试。

## Phase 3：实体消歧与角色档案

任务：

1. 根据姓名、别名、明确化名关系、共同经历和关系等生成实体匹配候选。
2. 将 canonical merge 与 unresolved candidates 分开；低置信度不自动合并。
3. 汇总角色的跨章节状态变化、性格行为依据、人物关系和出场章节。
4. 默认保留所有角色；提供 `importance`、`evidence_count`、`coverage` 等质量指标，而不是按 JSON 文件大小裁剪。

验收：

- 同名不同人、化名、译名变体、同一角色名/称号能有独立 fixture 测试。
- 所有合并有可追踪记录，可回滚。
- 不存在静默丢弃的角色。

## Phase 4：世界观、时间线与知识边界

任务：

1. 建立事件按章节排序的 timeline；保留发生时间与揭露时间的区别。
2. 为关键事实记录生效时间、失效时间和角色已知信息。
3. 产生冲突报告与未解问题，不自动覆盖证据。
4. 生成精简世界 Bible 和世界书规划表；区分常驻规则与按需条目。
5. 起始章节 N 只激活截至 N 可用的状态；未来原著事件不能出现在活动上下文。

验收：

- 自动化测试能发现“第 200 章才揭露的秘密出现在第 50 章状态”的泄漏。
- 没有明确时间的事件不得硬造绝对日期。
- 源材料冲突输出报告而非选一方悄悄覆盖。

## Phase 4.5：语义支持校验（`n2t verify`）

> 后加的一个阶段，插在原有 Phase 4 与 Phase 5 之间。
> 原计划的 Phase 编号保留不变，避免历史文档失去参照。

### 目标

回答「引文**支不支持**这条主张」—— 与 Phase 2 的「引文在不在原文里」是两件事。

### 为什么单独立一个阶段

引文 100% 定位只说明文本匹配成功。归属给错人、漏掉否定、把角色的信念当成
客观事实、只支持了复合事实的一半 —— 这四类错误**定位率全都能通过**。
它们必须由另一层判定。

### 判定

四分类：`entailed` / `partially_supported` / `contradicted` / `insufficient_evidence`。
只有前者算通过；`contradicted` 与 `insufficient_evidence` 的事实不进条目正文
（仍保留在 canonical 数据里）。`partially_supported` 按 §H 的口径**不排除**。

### 不做的事

- 不用一次调用处理多条事实（一次一条，判据独立）。
- 不在调用失败时静默跳过：单条记 `insufficient_evidence` 并写明原因，
  **一条都调不通则整体中止** —— 否则会静默清空世界书。
- 不把没跑过的说成跑过：未执行时写 `executed: false`。

## Phase 5：世界书与角色卡导出

任务：

1. 根据目标格式 serializer 生成主角色卡 V2，并内嵌 character_book。
2. 生成可单独导入的 worldbook JSON。
3. 默认 `description` 放简洁的世界模拟器运行规则；人物细节进入按需触发的世界书。允许通过配置调整。
4. 为常驻条目、角色条目、地点/组织/术语条目设计触发策略，并估算 Token 占用。
5. 生成引用清单和 audit report。

验收：

- JSON parser 与 schema validator 通过。
- 内嵌和独立世界书的条目语义一致，条目数量相同，除明确注明的包装差异。
- 所有关键字段与目标格式一致；没有模型凭空生成的额外字段。
- 输出不包含 API 密钥。

## Phase 6：质量评估与 Tavo 实测

任务：

1. 准备自制或公版的短文本 fixture，覆盖多角色、别名、剧透、关系变化和矛盾设定。
2. 运行端到端测试，人工检查来源覆盖、角色合并、世界书触发和 token 预算。
3. 将主卡和世界书导入 Tavo，记录实际行为（如果无法自动化，则提供人工验收步骤）。
4. 根据实测修复兼容性问题，而非只以 JSON parse 成功为准。

验收：

- 关键 NPC 可被正确触发。
- 常驻规则可以在无关键词命中的场景中生效。
- 角色不会提前知道未来事件。
- 运行中断可以恢复，旧产物不会被覆盖。

## Phase 7：后续增强（非 MVP）

- 单 NPC 独立角色卡导出。
- DOCX/EPUB 输入。
- 可选向量/全文检索以查找较长原文证据。
- 世界书触发命中测试与自动参数建议。
- 章节状态快照 GUI 或简单人工审校表。
- MVU/EJS/HTML 仅在用户明确提出后讨论。
